# Доменные документы

Как инженерные скиллы должны использовать доменную документацию этого репозитория при изучении кодовой базы.

## Перед изучением прочитать

- **`GLOSSARY.md`** в корне репозитория, или
- **`GLOSSARY-MAP.md`** в корне, если он есть: он указывает на один `GLOSSARY.md` на контекст. Прочитать каждый, относящийся к теме.
- **`docs/adr/`**: читать ADR, которые затрагивают область, в которой собираешься работать. В репозиториях с несколькими контекстами также проверять `src/<context>/docs/adr/` на контекстные решения.

Если каких-то файлов нет, **молча продолжать**. Не сообщать об их отсутствии и не предлагать создать их заранее. Скилл `/domain-modeling` (доступен через `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их лениво, когда термины или решения действительно появляются.

## Структура файлов

Репозиторий с одним контекстом (этот репозиторий):

```text
/
├── GLOSSARY.md
├── docs/adr/
├── app/
├── components/
├── lib/
└── agent/
```

Репозиторий с несколькими контекстами (при наличии `GLOSSARY-MAP.md` в корне):

```text
/
├── GLOSSARY-MAP.md
├── docs/adr/                          ← системные решения
└── src/
    ├── ordering/
    │   ├── GLOSSARY.md
    │   └── docs/adr/                  ← контекстные решения
    └── billing/
        ├── GLOSSARY.md
        └── docs/adr/
```

## Использовать словарь глоссария

Когда в результате упоминается доменное понятие (в заголовке issue, предложении рефакторинга, гипотезе, имени теста), использовать термин в том значении, которое определено в `GLOSSARY.md`. Не уходить к синонимам, которых глоссарий явно избегает.

Если нужного понятия в глоссарии ещё нет, это сигнал: либо ты придумываешь язык, который проект не использует (стоит пересмотреть), либо есть реальный пробел (отметить для `/domain-modeling`).

## Отмечать конфликты с ADR

Если результат противоречит существующему ADR, явно показать это, а не молча переопределять:

> _Противоречит ADR-0007 (event-sourced orders), но стоит пересмотреть, потому что…_
